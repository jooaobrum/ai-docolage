# Operations

This doc covers the two things ticket #25 added on top of the Service
(docs/spec/0002-docolage-service-off-databricks.md): running Workers on a
real GPU, and how the Sync gate / sync stream timeout defaults were
derived (and how to re-derive them on real hardware).

## Running the GPU worker image

The default `docker compose up` builds `worker` from `Dockerfile.service`
— a plain CPU image (`python:3.11-slim` + CPU-only torch, docling's
transitive dependency). It requires no GPU and no extra host setup, per
spec's MVP story ("no cloud account, no cluster, and no vendor").

To run Workers against a real GPU instead:

1. Install the [NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)
   on the host so Docker can see `nvidia` as a device driver.
2. Bring the stack up with the GPU override layered on top of the base
   compose file:

   ```
   docker compose -f docker-compose.yml -f docker-compose.gpu.yml up --scale worker=2
   ```

`docker-compose.gpu.yml` swaps the `worker` service's build to
`Dockerfile.worker-gpu` (an `nvidia/cuda:12.4.1-runtime-ubuntu22.04` base
with the CUDA wheel of `torch` installed before this package, so
docling's transitive `torch` dependency resolves to the GPU build rather
than falling back to a CPU wheel from PyPI) and requests one GPU per
Worker replica via `deploy.resources.reservations.devices`.

Worker replica count remains the scaling knob and is also the GPU count
(ADR-0010: "models are in-process"). See `Settings.worker_page_concurrency`
in `src/docolage_service/config.py` for the (separate) question of how
many Worker *processes* may safely share one GPU's VRAM — the worker loop
itself always processes one page at a time per process; see that
setting's docstring for the full reasoning.

## Measured defaults: Sync gate and sync stream timeout

The spec ("Unresolved, pending measurement") requires `sync_gate_max_pages`
and the per-Worker concurrency knob to come from a real benchmark run
over the existing sample documents, not a guess. `sync_stream_timeout_seconds`
(ticket #23) depends on the same measurement.

`benchmark/measure_worker_defaults.py` is that benchmark. It:

1. Loads `DoclingRecognizer` once (paying model-load cost up front, the
   same way a Worker process does).
2. Rasterizes and calls `recognize()` on up to `--max-pages-per-doc`
   pages (default 8) of every PDF in `benchmark/manifest.json` /
   `data/` — the same sample set `benchmark/eval.py` already scores
   against.
3. Reports mean/p50/p95/max per-page latency, and recommends:
   - `sync_gate_max_pages` = `target_seconds // mean_page_seconds`
     (default target: 45s wall-clock budget for a sync request)
   - `sync_stream_timeout_seconds` = `sync_gate_max_pages * mean_page_seconds * margin`
     (default margin: 2x, covering queue wait + slower-than-mean pages)
4. Writes the full report to `benchmark/worker_defaults.json`.

Run it with:

```
python benchmark/measure_worker_defaults.py
```

### Current defaults and how they were measured

Run on 2026-08-17, **CPU only** — no GPU was available in the sandbox
that ran this ticket:

```
python benchmark/measure_worker_defaults.py --max-pages-per-doc 5
```

14 pages sampled across all 4 files in `data/`
(`benchmark/manifest.json`): `CV JOAO BRUM.pdf` (1 page), `TSMCJ.PDF`
(3 pages), `paper.pdf` (first 5 of 16 pages), `stmicro-financial-report.pdf`
(first 5 of 469 pages). Model load: ~69s (paid once per Worker process
at startup, not per page). Per-page `DoclingRecognizer.recognize()`
latency:

| stat | seconds |
|------|---------|
| mean | 27.83 |
| p50  | 29.85 |
| p95  | 56.56 |
| max  | 56.56 |

Backed into a ~45s target sync wall-clock budget, `mean_seconds` floors
`sync_gate_max_pages` to **1** on this hardware — a real, not-guessed,
number, but a conservative CPU one (TableFormer + the OCR fallback path
dominate this cost and are expected to drop substantially on GPU).
`sync_stream_timeout_seconds` follows as `sync_gate_max_pages (1) x
mean_seconds (~27.8) x 2x margin ≈ 55.7s`, rounded up to **60s** — the
2x margin also covers the p95 case (56.56s) where a single slow page
alone would otherwise nearly exhaust the timeout.

This is a real measurement from the actual benchmark harness, not a
guess, but it is explicitly *not* a GPU number, and `sync_gate_max_pages
= 1` is a deliberately honest (if unglamorous) MVP default rather than
an inflated one — see the comment above each field in
`src/docolage_service/config.py`. See `benchmark/worker_defaults.json`
(generated by the run above) for the full per-document and percentile
breakdown backing those numbers.

### Re-running on real GPU hardware

Before relying on these defaults in production:

1. Bring up (or get access to) a Worker host with a real GPU — e.g. via
   `docker-compose.gpu.yml` above, or any host with a CUDA-capable GPU
   and `torch` built for it.
2. Re-run `python benchmark/measure_worker_defaults.py` on that host.
   GPU latency for docling's layout + TableFormer + OCR pipeline is
   expected to be meaningfully lower than CPU, which should let
   `sync_gate_max_pages` grow for the same wall-clock budget.
3. Update the two defaults in `src/docolage_service/config.py`
   (`sync_gate_max_pages`, `sync_stream_timeout_seconds`) to the new
   recommended values, updating the comment above each field to cite the
   new measurement date and hardware.
4. Commit the refreshed `benchmark/worker_defaults.json` alongside the
   config change so the numbers stay traceable to a specific run.

Both settings remain configurable via `DOCOLAGE_SYNC_GATE_MAX_PAGES` and
`DOCOLAGE_SYNC_STREAM_TIMEOUT_SECONDS` environment variables regardless —
re-measuring and updating the code default is about picking a better
out-of-the-box value, not a hard requirement to deploy on GPU.
